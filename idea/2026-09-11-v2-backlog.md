# RouteFinder — v2 Backlog

Date: 2026-09-11

Ideas explicitly deferred out of v1 (see "Out of scope" in [`2026-09-10-routefinder-design.md`](./2026-09-10-routefinder-design.md)), captured here in more detail so they aren't lost. None of this is built yet.

## Motorcycle-taxi / driver availability

The original idea that kicked off this whole app: showing whether an informal motorcycle-taxi is currently available near you, not just the route to take.

Why it's deferred: this isn't a routing feature, it's a second product — a driver-side app or interface, live GPS ingestion from drivers, a matching/dispatch layer, and probably some kind of driver onboarding/trust system. None of that exists yet, on top of everything already in v1 (routing + rewards + parking pilot).

Rough shape when picked up:
- `drivers` table: identity, vehicle info, verification status.
- Live location channel (websocket or short-poll) from the driver app to the backend.
- A `driver_status` concept (available/busy/offline) separate from a trip.
- Matching: rider requests a ride, backend finds nearby available drivers — this is the hard part (needs real dispatch logic, not just "nearest driver").
- Almost certainly needs its own design pass before touching code — this is bigger than everything currently in this repo combined.

## Public bicycle queue

Same shape of problem as bike/scooter-share systems generally: a bike sits at a station, gets checked out, gets returned somewhere (maybe a different station). Needs:
- `bike_stations` table (like `parking_spots`, but a station holds a *count* of available bikes/docks, not a single free/occupied flag).
- Check-out/check-in events tied to a user and a trip.
- Physical dependency: still needs bikes with some kind of lock/tracking, so it has the same "hardware blocks the software" issue as parking.

## Full parking system (beyond the 1-spot pilot)

The pilot (`parking_spots` table, already built) proves the sensor → backend → map pipeline end to end. Scaling it up needs:
- Actual procurement and installation of many sensors (hardware/logistics, not code).
- Possibly a lot-level aggregate view ("Lot A: 12/40 free") in addition to per-spot status, once there are enough spots for that to matter.
- Sensor health/liveness — right now a dead sensor just means a spot's `last_updated` goes stale forever; at scale this needs actual alerting.

## Real partner-merchant redemption

v1's `redemption_catalog` is admin-editable placeholder items (free coffee, print credit, etc.) with no real fulfillment. Real merchant integration needs:
- Actual partner agreements (business development work, not engineering).
- A fulfillment mechanism per merchant (a redemption code, a voucher, an API integration — depends entirely on who the partner is).
- Probably a `merchants` table once there's more than one, so catalog items can be grouped/attributed.

## Crowdsourced building nicknames

v1 aliases (`place_aliases`) are admin-only. Opening this to students needs:
- A submission flow (probably just "suggest a nickname" on a building's page).
- Moderation before a suggested alias becomes searchable (to keep out junk/abuse) — admin approval queue, not auto-publish.
